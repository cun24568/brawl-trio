# ブロスタ マッチング・隠しMMR解析プロジェクト 引き継ぎ資料

## 1. プロジェクト目的

ブロスタの**マッチング仕様と隠しMMRの挙動を解析する**。最終的にトロフィーモードのマッチング時間短縮にもつながる知見を得る。

## 2. 前提

- Supercellは「隠しMMRが存在する」と公式に言及している
- 内部MMR値・マッチングアルゴリズムは非公開
- 公式APIで取れるのは結果データ（バトルログ等）のみ

## 3. 既存資産

**自サイト brawl-trio.vercel.app**

- 6カ国TOP200プレイヤーの定期クロール(1時間ごと自動更新)
- マイページ登録プレイヤーのバトルログを30分ごとに蓄積
- トリオサバイバル特化のメタ集計UI(マップ別ティア、推奨編成、クラブ、ランキング、ルーレット)
- Vercelホスティング、データベース運用済み

## 4. 公式APIの取得可能/不可能

**取得可能**

- バトルログ(直近25戦):モード、結果、参加者全員のトロフィー、使用ブロウラー、タイムスタンプ
- プレイヤー情報、ブロウラー別トロフィー
- クラブ情報、ランキング

**取得不可**

- 内部MMR数値そのもの
- マッチング待機時間
- マッチングアルゴリズムのパラメータ

## 5. 解析の核となる問題:MMRの粒度

**重要な懸念**:隠しMMRがアカウント単位でモード共通の場合、トリオサバイバルのデータだけでTrueSkill等を当てても、観測できない他モードでMMRが変動しているため**観測欠損による推定バイアス**が発生する。

**3つのシナリオ**

- シナリオ1:MMRはモード共通 → トリオ単独解析は困難
- シナリオ2:MMRはモード別 → トリオ単独で完結可能
- シナリオ3:ハイブリッド → 部分的に可能

**したがって解析の最初のフェーズは「MMR粒度の検証」**。TrueSkill適用はその後。

## 6. 解析フェーズ

### Phase 1: MMR粒度の検証(最優先)

同一プレイヤーの全モードバトルログを時系列で並べ、「トリオの結果」と「他モードの直近勝敗」の相関を分析する。これでMMRがモード共通か別かを推定する。

必要データ:数百人分の、全モードバトルログ時系列。

### Phase 2: マッチング挙動の記述統計

- 9人のトロフィー分散をマップ別・時間帯別に集計
- 時間帯・地域・トロフィー帯ごとのマッチング条件緩和カーブ
- トリオ参加vs野良の検出(クラブ共起・連続共起から識別)
- パーティーの有無でマッチング条件がどう変わるか

### Phase 3: 隠しMMR推定

Phase 1の結果に応じて分岐:

- **モード別と判明した場合**:トリオ試合のみでTrueSkill適用。3チーム多人数なのでTrueSkill適合。
- **モード共通と判明した場合**:
  - 案A:全モードのバトルログを解析バックエンドで保存しTrueSkill適用(モード間スケーリングが必要、設計重い)
  - 案B:観測期間中トリオしかプレイしていない「トリオ専業プレイヤー」に絞って解析(サンプル減るが純度高い)
  - 案C:TrueSkillの時間減衰(σ拡大)で観測欠損を緩く補正

### Phase 4: 仮説検証

- 同トロフィー帯内での推定MMR分散と1位率の相関
- マッチ内9人の推定MMR分散 vs トロフィー分散の比較
- シーズンリセット前後でのMMR保持挙動
- ブロウラー単位 vs アカウント単位の検証

## 7. データ収集設計

**収集対象**

- 6カ国TOP200プレイヤー(継続)

## 解析結果アップデート (2026-05-16)

### Phase 1 簡易判定: モード共通スキル傍証
- 32人サンプルで Spearman 相関 (累計勝利 vs トリオtop2率)
- vDuo: rho=+0.46 (デュオ勝利数とトリオ強さに強い正相関)
- v3v3 / vSolo はほぼ無相関
- 暫定結論: 「サバイバル系 (trio/duo) でMMR連動、 3v3とソロは別」 のハイブリッド

### Phase 2: マッチング待機時間の間接推定
- `interval = battle_time_B - duration_B - battle_time_A` で連続戦闘の「ロビー+キュー」 時間を推定
- 全体中央値 ~136s (16,000ペア)
- モード別:
  - 3v3系 (gemGrab/brawlBall/knockout): 30-37s
  - サバイバル系 (solo/duo/trio): 125-161s
  - 必要人数が多いモードほど遅い
- 時間帯別: 深夜(2-5時) 115-118s → 22時ピーク 172s

### 高トロフィー帯のマッチング条件段差
- 1300台から徐々に上昇 → 1800で大ジャンプ (+1.6倍) → 2000で高止まり (~460s)
- チーム平均で見ると 2800台 で 600s (5倍)
- ★ ハイトロ帯ほどマッチング条件が階層的に厳しくなる (= 同帯人口減 + 精密マッチ追求)

### ★ 隠しMMR は (プレイヤー × ブロウラー) の単位
- Eve: JANET (highest 4417) で 744s (全体322sの2.3倍)、 PIERCE (highest 2896) で 447s
- 🍣: PIERCE (highest 2782, 32戦) で 490s (全体194sの2.5倍)
- 一方 サブアカ 🌓 (cur 3133, ガチElo 0) は MORTIS 223戦使用でも 126s
- → 「ブロウラー単位 highestTrophies + アカウント単位の生涯ガチElo」 が複合的に効く

### highestTrophies は刷新前のレガシーを保持
- KIT highestTrophies 10014 (current 2183) ← 旧トロフィー制度時代の値が残ってる
- ANGELO 4041, BULL 2746, FANG/MANDY 2280 等
- これがマッチング側で「過去の自分と同帯」 を探す指標として残り → 体感「刷新前主力キャラ使うと遅い」 の物証

### 連勝補正の検出
- WinStreak 0: 167s → 5-9連勝: 175s → 20+連勝: 181s
- 5連勝以上で +10-15s の遅化 (= サーバが「連勝中は強い側」 と判定して同帯精密マッチ強制)

### マッチ遅い時ほど勝てる現象
- rho(平均順位, gap) = -0.485 (gap長い試合ほど順位低い = 勝てる)
- rho(TOP2率, gap) = +0.456
- 解釈: 待たされる試合は同帯マッチが精密に組まれる → 自分が強い側に入りやすい
- 早いマッチに飛び込むと「弱い相手」 でなく「自分が低帯側」 になる可能性

### picks 逆相関の謎
- highest 1000-1999帯で picks(-0.560)が最強の逆相関
- 「ほとんど使ってない高highestキャラ (KIT/ANGELO等)」 は旧MMRが残ってる
- 「使い込んでる現主力」 は現MMRが現在トロと整合 → マッチ速い
- highest 3000+帯では逆転 (主力ほど遅い、 rho=+0.398)

### マッチング速度を上げる実用ガイド
1. **新リリースキャラを使う** (シリウス, ダミアン): highestTrophies が自然に低い → マッチング条件緩い
2. **旧主力 (highest 高) でも cur_trophies を下げて使えば遅化軽減** (LOLA/COLT パターン)
3. **連勝5以上で +15s 遅化** = 連勝が止まる方が次のマッチ早い (= 連勝補正の存在)
4. **サブアカ運用** (ガチバトル未プレイ + 総トロ低) が最強の解
5. **マッチ遅い試合 = 勝てる試合**、 急ぐより待つ方が成績は良い (rho 0.49)

## 補足:UseTrueSkillの基本コンセプト(参考)

TrueSkillはMicrosoftが開発した多人数・多チーム対応のレーティングシステム。各プレイヤーのスキルを正規分布 N(μ, σ²) で表現し、試合結果から逐次更新する。

- μ:推定スキル値
- σ:推定の不確実性(試合数が増えるほど小さくなる)

トリオサバイバル(3チーム×3人)はTrueSkillの自然な適用先。Pythonでは `trueskill` ライブラリでそのまま実装可能。


```python
import trueskill

env = trueskill.TrueSkill()
# 3チームの場合
team1 = [env.create_rating() for _ in range(3)]
team2 = [env.create_rating() for _ in range(3)]
team3 = [env.create_rating() for _ in range(3)]

# ranks=[0,1,2] は team1が1位、team2が2位、team3が3位
new_team1, new_team2, new_team3 = env.rate([team1, team2, team3], ranks=[0, 1, 2])
```

## 解析結果アップデート (2026-05-17) — 多角度検証セット

スクリプト: `scripts/mmr_multi_angle.py` + `scripts/mmr_trueskill_lose.py`
データ: 37プレイヤー × 16,770試合 (trioShowdown のみ、 全モードDB保存後の差分)

### A. 対戦相手側 trophies × gap の対称性 ★★★ 重要
| 指標 | rho |
|---|---|
| 敵チームの brawler trophies 中央値 | **+0.492** |
| 敵チームの brawler trophies 最大値 | **+0.535** |
| 試合内9人 (自分以外含む) trophies 中央値 | **+0.512** |

帯別検証:
- my_highest **0-1499** (N=11948) → 敵 trophies 中央値=**819**、 自gap=**123s**
- my_highest **1500-2499** (N=3525) → 敵中央値=**1604**、 gap=**174s**
- my_highest **2500-3499** (N=1142) → 敵中央値=**1790**、 gap=**441s**
- my_highest **3500+** (N=155) → 敵中央値=**1820**、 gap=**495s**

→ **「自分のMMR帯 = 敵 trophies 帯」 が直接観測できた**。 matchmaking は対称で、 相手側にも自分のMMRが反映されている。
→ 副産物: 自分のMMRを推定する代理変数として **「敵チームの brawler trophies 中央値」 が使える** (battlelog から直接観測可能)。

### B. (highest - current) 乖離 × gap の非線形ジャンプ
全体相関は rho=+0.005 (大半が乖離 100未満で埋もれる)。 帯別:
- 乖離 **0-99** (N=16232): 136s
- 乖離 **100-499** (N=221): 188s (+38%)
- 乖離 **500-999** (N=132): 202s (+49%)
- 乖離 **1000-1999** (N=107): **495s (+264%!)** ← 段差
- 乖離 **2000+** (N=78): 448s

→ **「乖離 ≧ 1000」 で旧MMR残存効果が劇的に発動**。 つまり MMRは「current trophies で見るのではなく highest を保持」 する明確な閾値挙動。

### C. クラブ内 MMR 連動 ★ 強い傍証
クラブ単位で gap中央値の分散を比較:
- クラブ内 平均分散 = **2,321**
- 全プレイヤー分散 = 17,559
- **内/外比 = 0.13** (1.0未満なら連動)

具体例:
- 🌕 (🌓+🌗、 サブ垢) spread = **8s** (126-134s)
- STORYTEAM (2人) spread = 8s
- バトロワオンリー (2人) spread = 18s
- バトロワ勢 8人 spread = 188s (構成員多様)

→ 同レベル者がクラブを組む傾向 → 結果的にクラブ内で MMR は揃う。

### D. マップ別 gap 分布
中央値遅い順 TOP3:
- **Molten to the Core**: 180s (rho=highest×gap **+0.715 ***)
- **Acid Lakes**: 152s (+0.509)
- **Gated Community**: 146s (+0.526)

最も平均が早い: Starfruit Supernova 128s / Feast or Famine 128s

→ マップ別 matchmaking pool が違う = 「マップ MMR」 が存在する可能性。 特に Molten to the Core は highest と gap の相関が突出して強く、 「ハイトロ専用マップ」 化している。

### E. 試合内 trophy 分散 × gap (仮説 逆!)
仮説「gap長いほど精密マッチで分散小さい」 は **不成立**。
- gap 0-60s: trio trophy var = **15,587** / 中央値 810
- gap 480+s: trio trophy var = **391,973** / 中央値 1,861

→ 25倍の分散差。 ハイトロ帯は「全員ハイトロ」 が揃わず、 「ハイトロ1人+残り低トロ」 のような構成で組まれている。 = **matchmaking はトロフィー値そのものを揃えるのではなく MMR を揃えている** (証拠強化)。

### F. ガチバトル経験量 × player gap (N=32)
| 指標 | rho |
|---|---|
| vDuo (デュオ勝利数) | **+0.434** |
| highestAllTimeRankedElo (生涯最高ガチElo) | **+0.380** |
| expLevel (経験値レベル) | **+0.357** |
| totalPrestigeLevel | +0.236 |
| rankedElo (現) | +0.217 |

→ 現ガチElo より **生涯最高ガチElo** の方が効く = アカウントMMRも「過去最高」 で測られる。 デュオ勝利数が最強なのは サバイバル系MMR共通仮説 (5月分析) と整合。

### G. 「乖離大ブロウラー」 多く所持 × player gap
- 乖離 500+ のブロウラー数 × gap: rho=**+0.411 **
- 乖離合計 × gap: rho=**+0.452 **

→ **古参指標 (乖離キャラ保有数) が単体 player gap に効く**。 単に「過去栄光ブロウラーを持ってる」 だけでなく、 アカウント全体の累積 MMRシグナルとして使われている。

### H. ハイチャ装備有無 × gap
- HC所持 ブロウラー: N=10,756  gap中央値=**153s**
- HC無し: N=6,014  gap中央値=**118s**
- 差: **+35s (29% 遅化)**

→ ハイチャ取得 = そのブロウラー使用率高 = 当該ブロウラーMMRが上昇 → 遅化。 「ハイチャ未取得キャラ」 が早マッチの実用ルート。

### I. 連続gapの自己相関 (lag=1)
- rho = **+0.435** (N=16,246)

→ 「遅い試合の次は遅い、 早い試合の次は早い」 の強い持続性。 短期的にMMR帯がジャンプしない = サブ垢的な動きでは抜けられない。

### 総合解釈 (2026-05-17 時点)

1. **MMR は明確な状態量**: 連続gap自己相関 (+0.435)・帯別非線形 (乖離1000段差)・クラブ内連動 (0.13)・敵trophy 対称性 (+0.49) から、 単一の隠れ変数として強く存在。

2. **「強い側」 認定の主要因 (寄与順)**:

- ✅ **bot の装備セット (= バトルカード) でbot強さが決まる**

### 公式 battlelog API の制約
battlelog の bot プレイヤーの `brawler` オブジェクトに含まれるフィールド:
```json
{ "id": 16000020, "name": "FRANK", "power": -1, "trophies": -1 }
```
- `gadgets` / `starPowers` / `gears` / `hyperCharges` の **装備情報は一切含まれない**
- → **公式APIから botのバトルカードは直接観測不可能**

### 取得可能な情報
- bot brawler 種類 (id/name) のみ → 「練習試合で何のキャラが出るか」 は分かる
- ただし装備セットは見えない

### duration相関の再評価
前版で報告した「obs_MMR × duration rho=+0.627 (N=20)」 は **サンプリングバイアスの疑い**:
- 主タグ #YQ8YY09R の19戦は全て duration が -4〜-7秒 (= ロビーで即抜け)、 これらは「観察ベースMMR=1773」 で本来の練習試合データではない
- 残り少数サンプルが他プレイヤーで durationまとも → 結果として偽の相関が出た可能性高
- **duration はMMR推定の指標として却下** (ユーザ指摘通り)

### botの装備カードを取得する 3つの実装案

#### 案 X1: ユーザ手動入力フォーム (実装容易)
- マイページに「練習試合 bot装備記録」 フォーム追加
- ユーザが練習試合後に bot の装備を手動入力:
  - Star Power 名 (2択)
  - Gadget 名 (2択)
  - Gear 種類×個数 (最大4)
  - HyperCharge 有無
- DB の `bot_training_observations` テーブルに保存し、 観察ベースMMR と相関分析
- メリット: 公式API依存しない、 すぐ実装可能
- デメリット: ユーザ協力前提、 サンプル収集が遅い

#### 案 X2: C案 (パケット解析) で装備データ intercept
- mitmproxy + Frida で friendly 試合のサーバ→クライアント パケットを解読
- bot の装備データはクライアント側に確実に送られる (描画のため)
- `packet-analysis/bs_extract.py` で `BattleStartMessage` payload を解析、 bot brawler の装備リストを抽出
- メリット: 自動収集可能、 大量サンプル
- デメリット: 規約違反、 サブ垢必須、 プロトコル解読に2-3週間工数

#### 案 X3: 画面OCR (画像認識)
- ゲーム画面のスクリーンショットから bot brawlerアイコンと装備を画像認識
- 既存研究 (Brawl Insights 等) で類似手法があるか調査
- デメリット: 精度低い、 UI改修で都度壊れる、 ストレージ重い

### 推奨ルート
1. **X1 (手動入力) を即実装** → サンプル N>=30 程度集める
2. その時点で「観察ベースMMR帯 × bot装備セット」 の相関が見えるか確認
3. 強い相関 (rho>0.4等) が確認できたら X2 (パケット解析) に移行して自動化

### ユーザ仮説の再評価
- ❌ 試合時間からのMMR推定: 既存研究の delusionで、 採用しない
- ✓ **「botのバトルカード装備でMMR帯が判別できる」 仮説は依然有力**: ただし公式APIから直接観測不可能、 手動入力 or パケット解析が必要

### 既存知識として
- ユーザ自身が実際にゲーム内で botのバトルカードを目視確認している → 経験則として「MMR帯ごとに bot 装備が違う」 を確信
- 既存研究 (Brawl Stars 海外コミュニティ) でも同様の観察報告あり (要再調査)
